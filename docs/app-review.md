# App / System / Core 集成审查

## 1. 总体结论

审查范围为 `src/Cap.App`、`src/Cap.System`、`src/Cap.Core`，并追踪 `RecordingSession.StopAsync/Run/Dispose` 与 `RecordingRecovery` 的调用契约。侧重会话生命周期、失败事件、退出、恢复、设置、热键和 DPI 坐标。审查期间没有修改这些模块。

以下位置对应修复前审查快照。问题已向主实现代理报告，主实现代理正在修复；本报告不把“已通知”视为“已修复并验证”。

发现两个明确功能缺陷，以及四项稳定性/体验问题。既有 System/Core 自动检查全部通过，但这些检查未覆盖 UI 调度时序。

## 2. 阻塞问题

### [P1] 旧录制失败回调可以停止新录制

- 位置：`src/Cap.App/App.xaml.cs:94`，关联 `src/Cap.Recording/RecordingSession.cs:159–160`。
- 确定性：确定存在可行线程交错，尚未运行针对该交错的自动压力复现。
- 问题：录制线程先 `completion.TrySetException`，后触发 `Failed`；UI 的 `Failed` 回调调用使用可变全局 `session` 的 `StopRecordingAsync()`，没有检查事件是否来自当前会话。
- 复现时序：用户停止 A → A 失败并完成其 Task → UI 处理停止失败，清理 A → 用户启动 B → A 线程随后触发或投递 `Failed` → UI 回调停止 B。
- 影响：新录制被无关的旧异常提前结束。
- 建议：排队之前和执行回调时检查 `ReferenceEquals(session, recording)`；Progress 回调也应用同样的会话身份约束，避免旧状态写入新控制条。

### [P2] 恢复其他目录的 GIF 日志时错误命名为 MP4

- 位置：`src/Cap.App/App.xaml.cs:147–149`；预览类型选择位于 `src/Cap.App/PreviewWindow.cs:30–37`。
- 确定性：代码路径确定；未运行跨目录系统文件对话框复现。
- 问题：恢复格式只从默认保存目录的 `candidates` 中查找。用户在文件对话框选择其他目录的 GIF `.capjournal` 时，candidate 为 null，输出扩展名默认为 `.mp4`。恢复编码器使用日志头的真实 GIF 类型，因此最终文件是 GIF 数据加 MP4 扩展名。
- 影响：预览错误选择视频播放器；其他程序也可能无法识别/打开恢复结果。
- 建议：根据用户最终选择的日志读取真实元数据后生成输出路径，不能用“默认目录中是否存在该文件”推断编码格式。

## 3. 建议修改

### [P2] 退出时没有等待已经进行中的异步停止

- 位置：`src/Cap.App/App.xaml.cs:100`、`:162`、`:167`；关联 `RecordingSession.Dispose:231–235`。
- 确定性：确定控制流问题。由于 Dispose 会同步等待，目前不能据此断言输出文件必然损坏。
- 复现：录制较长内容并点停止；编码器仍在收尾时从托盘退出。
- 问题：第二次 `StopRecordingAsync()` 因 stopping 提前返回一个已完成 Task，ExitAsync 随即 Shutdown；OnExit 再通过 Dispose 在 UI 线程同步等待录制结束。
- 影响：退出期间主线程可能长时间无响应；正常停止的结果/异常续体无法按预期运行。保存失败也不能可靠通过原来的异步 UI 路径呈现。
- 建议：保存共享的停止 Task，每次停止/退出都等待同一个 Task；Shutdown 应发生在该 Task 真正完成之后。

### [P2] 截图或录制设置取消后没有恢复之前可见的设置窗口

- 位置：`src/Cap.App/App.xaml.cs:66`、`:85`。
- 确定性：确定。
- 复现：打开设置 → 触发截图或录制 → Esc/取消。
- 问题：设置窗口被 Hide，finally 仅清除 busy，没有记录/恢复原可见状态。
- 影响：原本正在编辑的设置窗口突然消失，只能从托盘重新打开。
- 建议：记录流程开始前的可见状态，在取消/失败/截图完成且未退出、未开始录制时恢复；不要在真实录制开始后重新显示并录入画面。

### [P2] 控制条可能放入不规则多显示器布局的空洞

- 位置：`src/Cap.App/RecordingControlWindow.cs:42–48`。
- 确定性：坐标计算确定；尚未在真实不规则布局验证。
- 复现布局：主屏 `(0,0,1920,1080)`，副屏 `(1920,0,1920,2160)`。录制主屏时控制条首选 y=1088，而此处 x=0..控制条宽度没有显示器。该坐标仍落在虚拟桌面外接矩形内，因此不会触发回退。
- 影响：控制条完全不可见，暂停/停止按钮不可操作，用户只能依赖全局快捷键停止。
- 建议：选取录制区域所在的真实显示器边界，在该显示器内部放置控制条；同时使用目标显示器 DPI 计算实际宽高。

### [P2] 退出不等待或取消正在进行的恢复

- 位置：`src/Cap.App/App.xaml.cs:151` 与 `:158–162`。
- 确定性：确定恢复 Task 没有被 ExitAsync 跟踪；未测试真实长恢复中退出。
- 问题：恢复时只有 busy 标志，退出只关心 session。用户在恢复途中退出，进程会在后台恢复任务结束前关闭。
- 影响：当前恢复无法完成，可能留下 `.recovering.*` 临时输出；原始日志保留，因此不能据此断言原始录制丢失。
- 建议：跟踪恢复 Task 和取消令牌；退出时明确取消并等待释放编码器，或等待恢复完成后退出。

## 6. 风险总结

主要风险是多个异步操作共同使用可变的 App 会话字段，和把虚拟桌面外接矩形误当成真实显示区域。配置校验、损坏文件保留、热键注册失败回滚、托盘图标句柄释放和预览关闭释放路径在已读范围内未发现其他明确阻塞问题。该结论来自代码阅读和上述 9 项自动检查，不代表尚未执行的 UI/设备场景已通过。
